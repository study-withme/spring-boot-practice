# Mini Blog (연습·포트폴리오)

신입 백엔드 개발자로서 **Spring Boot**로 블로그 백엔드를 단계적으로 만들어 가는 개인 프로젝트입니다. 
기능을 조금씩 붙이며 API 설계, 영속성, 예외 처리 등을 익히는 것이 목표입니다.

## 1. 이 레포지토리에서 하는 일

- REST API 기반의 소형 블로그 백엔드 구현
- 혼자 순차적으로 범위를 나누어 커밋·기능 단위로 확장
- 구현·디버깅 과정에서 마주친 이슈를 **트러블슈팅 목록**으로 남기고, 필요 시 외부 글·노트와 연결

## 2. 기술 스택

| 구분 | 사용 |
|------|------|
| 언어·런타임 | Java 25 |
| 프레임워크 | Spring Boot 4.0.x (`practice/build.gradle` 기준) |
| 빌드 | Gradle |
| 웹 | Spring Web MVC |
| 데이터 | Spring Data JPA |
| 기타 | Lombok, Spring Boot DevTools (개발) |

## 5. 도메인 정책

해당 섹션은 '개발자 일기(mini blog)'라는 프로젝트 컨셉에 맞게, **제품 관점에서의 가정과 현재 코드가 그 가정을 어디까지 반영하는지**를 구분하여 정리한 도메인 정책입니다. API·필드별 세부 규칙은 각 도메인 README를 기준으로 합니다.

<details>
<summary><strong>도메인 정책 전체 펼치기</strong></summary>

API와 도메인 규칙을 한곳에서 읽을 수 있도록, **제품 관점에서의 가정**과 **현재 코드가 그 가정을 어디까지 반영하는지**를 구분해 두었습니다. 세부 API·필드는 각 도메인 README를 기준으로 합니다.

<details>
<summary>공통 가정</summary>

- **신뢰 경계(학습용)**: 별도의 로그인 세션·JWT 없이, 글·댓글 수정/삭제 등에서 필요한 `userId`는 **클라이언트가 쿼리/바디로 넘긴다**고 가정합니다. 실서비스에서는 인증 주체(Principal)와 일치 검증으로 바꾸는 것이 맞습니다.
- **실패 표현**: 규칙 위반은 주로 `IllegalArgumentException`과 메시지로 처리합니다. HTTP 상태·본문 형식은 전역 예외 처리로 정리할 여지가 있습니다.
- **시간**: 생성·수정 시각은 엔티티의 `@PrePersist` / `@PreUpdate` 또는 필드 직접 설정 등 **구현별**로 맞춰져 있으며, 회원(`User`)의 감사 필드는 게시글·댓글과 완전히 동일하지 않을 수 있습니다.

</details>

<details>
<summary>게시글(Post) 정책</summary>

| 구분 | 가정·규칙 | 현재 구현 메모 |
|------|------------|----------------|
| 삭제 방식 | **소프트 삭제** — `deleteTime`이 있으면 “삭제된 글”로 보고 목록·단건 노출에서 제외 | `deleteTime` 설정으로 일치 |
| 조회 범위 | 목록·단건·작성자별 목록은 **미삭제 글만** | `deleteTime IS NULL` 조건으로 일치 |
| 수정 권한 | **작성자만** 수정 가능 | `userId`와 게시글의 작성자 id 일치 시에만 수정 |
| 삭제 권한 | **작성자만** 삭제 가능하는 것이 자연스러움 | `DELETE /api/posts/{postId}?userId=` 로 **작성자 `userId` 검증** 후 소프트 삭제 ([POSTREADME.md](POSTREADME.md)) |
| 조회수 | 글 단건 조회 시 조회수를 올릴 수 있는 도메인으로 둘 수 있음 | **단건 조회(`GET /api/posts/{postId}`) 시 `viewCount` 1 증가** |
| 입력 검증 | 제목·본문 길이 등 API 계약을 맞출 것 | **생성·수정 요청 모두** 동일한 Bean Validation 규칙 적용 |

</details>

<details>
<summary>댓글(Comment) 정책</summary>

| 구분 | 가정·규칙 | 현재 구현 메모 |
|------|------------|----------------|
| 구조 | 게시글당 댓글은 **최대 2단**(루트 → 대댓글), 그 아래 답글 불가 | 부모의 부모가 있으면 답글 생성 거부 |
| 삭제 방식 | **소프트 삭제** | `deleteTime` 설정, 목록은 미삭제만 |
| 수정·삭제 권한 | 해당 **게시글에 속한 댓글**이어야 하고, **작성자 `userId`** 와 일치해야 함 | `postId`·작성자 검증 일치 |
| 표시 이름 | 과거 댓글은 작성 시점 기준으로 보이게 할 수 있음 | **닉네임 스냅샷**(`nickname`) 저장 |
| 부모 글 삭제 | “글 삭제 시 하위 댓글을 어떻게 할지”는 제품 선택 | **명시 정책 없음** — cascade·노출 규칙은 추후 결정 |

</details>

<details>
<summary>회원(User) 정책</summary>

| 구분 | 가정·규칙 | 현재 구현 메모 |
|------|------------|----------------|
| 가입 | 로그인 id(`username`)는 **유일**, 닉네임도 가입 시 **중복 불가**로 둠 | `existsByUsername` / `existsByNickname`으로 검증 |
| 비밀번호 | 평문 저장 금지 | **BCrypt** 인코딩 후 저장, 로그인 시 `matches` |
| 로그인 응답 | 비밀번호는 내려주지 않음 | `UserResponse`에 비밀번호 필드 없음 |
| 회원 삭제 | 탈퇴 시 데이터 처리 방식은 제품 선택 | **물리 삭제** (`repository.delete`) — 연관 게시글·댓글과의 FK 정책은 스키마·실행 순서에 따름 |
| 정보 수정 | 아이디·닉네임 변경 시 타인과 겹치지 않게 할 수 있음 | **`existsByUsernameAndIdNot` / `existsByNicknameAndIdNot`으로 타인 중복 시 거부** |
| 관리자 | 역할(`Role`) 필드는 확장 여지 | API·보안에서 역할별 제한은 **아직 없음** |

</details>

정책을 바꾸거나 구현을 맞출 때는 이 표를 함께 갱신하면, 포트폴리오를 보는 사람이 **의도와 코드의 차이**를 빠르게 파악하기 쉽습니다.

</details>
